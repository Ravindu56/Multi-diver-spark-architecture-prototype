## 1. Summary

- **What it does.** Before a K-Means or logistic-regression (LogReg) job starts,
  the predictor estimates, for each Spark driver, the CPU it will use (95th
  percentile and mean, in cores) and the memory of the largest driver (95th
  percentile and peak RSS, in MB), each with an upper bound.
- **Accuracy in range.** On the frozen test split the typical error (MAE) is
  0.47 cores for CPU p95 (8 %) and 98 MB for memory p95 (6 %). Identical
  repeat runs differ by a standard deviation of 0.36 cores and 99 MB, so the
  errors are close to the run-to-run noise of the testbed.
- **Beyond the measured range** (E1, 300–400 MB): errors stay similar
  (0.51 cores, 147 MB, 6–7 %), but CPU p95 and memory were under-predicted
  in every such run. The
  upper bound covered all CPU and memory-p95 runs and 5 of 6 peak-memory
  runs. Beyond the range the allocator must therefore use the upper bound,
  not the point prediction. Only 3 configurations were available for this
  check.
- **Upper bounds in range.** Real use stayed within the upper bound in
  85–93 % of test rows (target 90 %). K-Means CPU p95 is the weak spot
  (75 %), because identical K-Means runs vary by ±0.41 cores.
- **Transfer learning (Scout).** It was implemented and tested in three ways.
  - Using Scout's host-level labels as per-driver labels does not work: a
    negative result, reported in section 6.
  - Scout's growth trend helps only when local data cannot show a trend. With
    the current data it gives the same answer as the local data, so it is
    kept as an automatic fallback for LogReg memory.
  - The deployed predictor's accuracy comes from the local data.
- **One predictor.** There is one entry point (`ResourcePredictor`). It uses
  a random forest per workload for CPU and a Ridge per workload for memory,
  with a power law for K-Means peak memory.

**Definitions**

| Term | Meaning |
|---|---|
| MAE, RMSE | mean absolute and root-mean-square error, in cores or MB |
| bias | mean of (predicted − actual); negative means under-prediction |
| under-predicted | share of rows with predicted < actual; about 50 % for an unbiased model |
| above upper bound | share of rows with actual > upper bound. For memory this is the share that would exceed a container limit set at the upper bound |
| R² | pooled and per workload. Reported only with at least 3 configuration groups, and to be compared with the **noise ceiling**: the R² of the mean of replicate runs (Sets D + E2), which no model can beat on average |
| 95 % CI | group bootstrap: 2000 resamples of configuration groups, the independent unit |
| rows | CPU: one row per driver. Memory: one row per run (the largest driver; every driver gets the same limit) |

## 5. Upper bounds (safety limits)

How the upper bounds are set:
- **Inside the measured range:** the 0.9 quantile of out-of-fold errors
  (leave-one-configuration-out CV on train + validation), per workload. CPU
  for LogReg uses a relative margin, since it was the narrowest method with
  calibration-CV coverage ≥ 0.88 (step A3, `scripts/upper_bound_tests.py`).
- **Beyond the largest measured data per driver or cores:** a floor from
  train + validation stress tests that hold out the larger jobs:

| target | beyond the largest measured | workload | floor | held-out rows (groups) |
|---|---|---|---|---|
| cpu_cores_p95 | data per driver | kmeans | prediction + 28 % | 72 (15) |

What the coverage numbers mean (from the "above upper bound" column in 4.1):
- **Memory is a hard limit in Docker:** exceeding it means an OOM kill. Of
  the test runs, 7 % (p95) and 10 % (peak) were above the upper bound. On E1
  interior it was 6 % and 6 %; on E1 extrap, 0 % and 17 %. So the allocator
  (step B) must add its own margin for memory limits, and memory limits must
  be tested with real `docker --memory` caps. Memory caps were not enforced
  during data collection (handoff caveat 5).
- **CPU is a soft limit:** exceeding it means throttling and a slower job,
  not a failure. On the test split, 15 % of rows were above the upper bound
  (K-Means: 25 %).

### 6.2 Scout growth trends beyond the measured range (`scripts/transfer_trend_tests.py`)

Demand is modelled as ∝ x^β along data per driver (size) or cores. The trend
is applied only beyond the largest measured x. The methods:
- `local`: the model's own prediction;
- `flat`: no growth;
- `scout_trend`: β from Scout;
- `local_trend`: β from the local rows;
- `combined`: the Scout-informed β = (n·β_local + 3·β_Scout)/(n + 3).

The tests:
- **size S1** (scarce): train ≤ 50 MB, predict > 100 MB;
- **size S2**: train ≤ 100 MB, predict > 100 MB;
- **cores C1**: K-Means trained on ≤ 2 cores, predicting 3–4; LogReg trained on
  ≤ 4, predicting 6–8.

A dash means the β was not available (the local data showed no trend).

### 6.4 Verdict on transfer learning

Transfer learning was carried out as planned, under rules fixed before each
test:
- Scout was audited and its labels were mapped;
- three label-transfer methods were tested;
- two trend-transfer methods were tested;
- the methods were compared in CV, on a learning curve and on the test split.

The result is negative for labels and neutral for the deployed predictor on
the current data. The deployable model is local, and Scout contributes a
fallback size trend. This is the outcome the architecture allows for
(section 6, item 5): "use Scout for auxiliary trend analysis … make the
local-only per-driver predictor the deployable model". The thesis should
report it as such, not as a transfer gain.

| set | exact_configs | exact_configs_in_train_val | groups_in_train_val |

| E1 interior | 8 | 0 | 0 |

Groups in more than one split: 0. Post-run columns among the inputs: none. Heap is an input: False.

- **E2 overlaps training by design.** Its configurations are also in
  training, which is why it is used only for the noise ceiling.
- **The inputs are pre-launch only:** workload, dataset MB, workers, cores,
  planned iterations, features and k, plus data per driver and its products.
  - No measured value (wall time, CPU, memory, sample counts or realised
    iterations) is an input.
  - The heap is not an input.
  - Scaling is fitted inside each pipeline on training rows only.

Comparison with the partner's independent cross-check (`predictor_handoff.md`,
gradient boosting). The handoff says to use it "only to detect leakage or a
broken split":

| Check | Partner reference | This predictor |
|---|---|---|
| grouped CV R², CPU p95 | 0.67 (5-fold on A+B+D) | 0.780 (leave-one-configuration-out on train + validation; forest per workload) |
| grouped CV R², memory p95 | 0.87 | 0.881 (Ridge per workload) |
| E1 interior R², CPU / memory | 0.85–0.96 / 0.81–0.89 (trained on A+B) | 0.981 / 0.901 |

The cross-validation numbers are of the same size, so there is no sign of
leakage. The E1 values are higher for three reasons:
1. this predictor is trained on A+B+D (Set D adds the core sweeps), against
   A+B;
2. it has one model per workload;
3. on 3 groups, the pooled R² is inflated by the gap between workloads.

MAE is the safer comparison.

## 10. Limitations

- **Small data.**
  - There are 88 configuration groups in all: 14 test groups, 8 for E1
    interior and 3 for E1 extrap, so the intervals are wide.
  - The test split and E1 were seen during steps A1–A3, so they are not
    blind.
- **One laptop-class host, one job at a time.** No claim about contention or
  cloud scaling can be made.
- **Valid only for the measured settings** (see the model card for the
  ranges):
  - heap of 3,072 MB (K-Means) and 6,144 MB (LogReg);
  - thread cap = cores.
- **Beyond the measured range the predictions are biased low.** Safety there
  rests on growth trends and stress-test floors checked on 3 configurations.
- **K-Means CPU p95 upper bounds cover 75 % on test,** because of run-to-run
  noise.
- **The memory label is RSS** (PSS is empty), not cgroup memory, and has not
  been validated against OOM.
- **Possible improvements found during A4.** The deployed predictor is
  unchanged.
  1. In CV, the power-law Ridge (`ridge_log_wl`) also has lower error for
     LogReg memory (p95 212 vs 273 MB; peak 204 vs 262 MB). Step A2 tested it
     for K-Means only. Testing LogReg memory under the same A2 protocol (an
     in-range paired CI plus the extrapolation check) is a candidate next
     step.
  2. Beyond 8 LogReg cores, the Scout-informed core trend beat the model's own
     memory prediction (section 6.2). This matters only if more than 8 cores
     per LogReg driver are ever allowed.

## 11. Decisions for the supervisor

1. **Memory R² ≥ 0.90 (old backlog target).**
   - It is met on the pooled test split (0.942) and on pooled E1 interior
     (0.901).
   - It is not met per workload (K-Means test 0.734; LogReg E1 interior
     0.649).
   - The architecture advises against a fixed R² threshold. Proposal: judge
     the predictor on MAE in MB and cores, and on upper-bound coverage
     (target 90 %).
2. **Transfer learning.** Accept the Scout outcome: negative label transfer,
   with Scout kept as a fallback trend.
3. **Model families.** Accept a random forest for CPU (CV MAE 0.71 vs 1.23
   cores for Ridge per workload) with Ridge for memory. The original plan
   named Ridge as the primary model.
4. **Memory label.** Accept the RSS of the largest driver (95th percentile and
   peak) as the memory label.
5. **Safety level.** Accept the 0.9 quantile as the safety level of the upper
   bounds.
6. **Scope.** One host, no contention. The Docker memory-limit validation
   belongs to step B (the allocator).
